1. Purpose and scope

This document explains how to install, run, understand, test and maintain the SuperAsk.AI prototype shown at Demo 1. It is written for a developer or technical reviewer working from the project repository. The user-facing guide is the separate User Documentation.

SuperAsk.AI is a Next.js web application with one shared question-answering engine. Three entry points use that engine: the web chat, a Telegram bot and a Telegram Mini App. The engine answers only from an approved knowledge base, attaches the official source to every answer, and declines when no source supports an answer.

Status. This is a course prototype. The knowledge base is a sample corpus built from public ministry pages; it has not been formally approved by government content stewards. Fees and deadlines in it must not be treated as official.

Each of those folders holds a README that points to the real location.

4. Installing and running

Requirements: Node.js 22 or newer (the version CI uses), npm, and an internet connection for the first install. Windows, macOS and Linux all work.

  1. Clone the repository and open its root folder:
    git clone https://github.com/Monunhh/Super-ask.git
cd Super-ask
  2. Install the dependencies:
    npm install
  3. Create a local settings file. macOS and Linux: cp .env.example .env.local. Windows PowerShell: Copy-Item .env.example .env.local.
  4. Start the development server and open http://localhost:3000:
    npm run dev
  5. Optional production build: npm run build, then npm start.

No model credential is needed. Without one, the engine uses its deterministic extractive mode, which quotes the approved source passage directly. Answers from a model-backed deployment are worded differently but use the same sources and gates.

5. Configuration

Settings are environment variables, documented in .env.example. Keep real keys in .env.local locally and in the host's secret settings in deployment; never commit them, and never expose them to browser code.

6. Architecture and request processing

All three entry points call one function, ask() in lib/engine/, so the web chat, the bot and the Mini App always give the same answer to the same question. The engine has three tiers: a human-approved curated answer served verbatim (tier 1), retrieval-augmented generation over the knowledge base (tier 2), and a decline (tier 3). A question passes through these stages in order:

#StageWhat it does
1Guardrail screenDeclines emergencies, legal advice, personal cases, predictions, political and off-domain questions before any retrieval or model call
2Curated matchServes an approved curated answer verbatim when the question matches one
3RetrievalKeyword and Khmer-aware search over data/kb/, aliases for query expansion, rank fusion and re-ranking
4Confidence gateDeclines when the best passage scores below the decline floor, so weak retrieval never reaches generation
5GenerationWrites the answer from the retrieved passages only, in the language of the question
6VerificationChecks figures and claims against the sources; suppresses an answer that states something the sources do not
7Output moderationFinal policy check on the written answer
8Citation assemblyAttaches ministry, document, effective and last-verified dates, review status and link

Every answer, including declines, is written to an audit record (question, retrieved source IDs, model and prompt version, answer, verification outcome) after personal data such as phone and ID numbers has been redacted.

The knowledge base and the monitored websites are kept apart: the crawler records that an official page changed, but fetched text never becomes answerable automatically. A person must review it and update data/kb/.

7. API routes and the Telegram integration

RoutePurpose
POST /api/askTakes a question (required, at most 1,000 characters) and recent history; returns the answer or decline, citations and confidence. An unexpected error returns a safe decline, never an unsupported answer.
POST /api/feedbackRecords a report or rating on an answer, with its answer ID and citations, comment redacted
GET /api/healthHealth check for deployment monitoring
POST /api/telegram/webhookReceives Telegram updates, checks the webhook secret, answers through the same engine and replies in Khmer or English with a Mini App button

To connect a bot, set the token and webhook secret, then register the webhook from a trusted machine:

npx tsx scripts/telegram-webhook.ts set https://<host>/api/telegram/webhook

Data collection scripts are described in docs/demo-1/4_data_collection/README4.txt. In short: npm run build-sources regenerates data/sources.json from the registry; npm run crawl:verify checks every registered site; npm run crawl:monitor detects changed pages. The crawler respects robots.txt, identifies itself, and waits at least 2 seconds between requests to the same host. Do not edit sources.json by hand.

10. Continuous integration

GitHub Actions (.github/workflows/ci.yml) runs on every push to main and every pull request, on Ubuntu with Node.js 22 and no model credential, so no paid model is ever called. The steps are: install with npm ci, type check, tests with coverage thresholds, production build, the retrieval and refusal evaluation, and the quality gates. A drop below the coverage floor or the evaluation targets fails the build.

11. Deployment and maintenance

  • Deploy by building the project on the host with the environment variables set there, then check GET /api/health, the web chat and the Telegram bot.
  • After changing the engine, retrieval rules, glossary, aliases or knowledge base, run npm run check before merging; CI runs it again.
  • To add content, add passages to data/kb/ with source URL and dates, add evaluation questions to data/golden.json, and re-run the evaluation.
  • Audit and feedback logs in var/ are git-ignored; personal data is redacted before it is written.

12. Known limitations

  • The knowledge base is a small sample covering five service areas, not yet approved by ministry stewards.
  • The login and register screens are prototypes; there are no real user accounts yet.
  • There is no reviewer portal yet for changes found by the crawler.
  • Ranking puts the right source first 67.6% of the time; improving this is planned before Demo 2.
  • Telegram follow-up memory can be lost when the serverless host restarts.
  • The office directory (UC-7) has two entries; map links are planned.
